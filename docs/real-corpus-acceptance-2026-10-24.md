# 真实长篇一致性验收（30 万字 × 3 部）— 2026-10-24

`docs/consistency-baseline-2026-10-23.md` 定的验收口径是「30 万字 × 3 部真实作品」，一直卡在
「需要 AI 把正文抽成 assertion」这一段（本机无任何 provider 凭据）。本文记录第一次把它**真跑通**：
原文是公版长篇，落库、采纳、引擎全部走生产路径，只有抽取器换成了确定性规则。

## 1. 之前卡在哪，怎么绕开的

`backend/moyu_extract.py` 那条 AI 抽取链路需要 provider。本机实测无凭据：
`env` 无 API key、`moyu.sqlite3` 0 字节、无 `.moyu*` 配置文件；`backend/moyu_provider.py` 在 `list_models()` 与请求构造处各做一次相同的密钥格式校验（`invalid_configuration`）
的调用在没有 key 时直接抛错。所以「真实稿件 → AI 抽取 → assertion」这一步跑不起来。

`benchmarks/real_corpus/extract_rules.py`（258 行）把这一步换成**确定性规则**：抽得少，但抽出来
的是真事实，而且能对着原文复核。规则表（精度优先，不追召回）：

| 规则 | 形状 | 处理 |
| --- | --- | --- |
| `姓X名Y`（可带 `字Z`） | 姓曹名操字孟德 | 命中即真名。三国 100 条、水浒 141 条、红楼 5 条 |
| `身长X尺` | 身长八尺、身长八尺四五 | 命中即身高 |
| `年方X岁` | 年方十八岁 | 命中即年龄 |
| `A字B` | 曹孟德字孟德 | **只在 A 已是册内实体 + B 过名字用字闸门**时才采用 |
| `绰号/浑名` | 黑旋风、豹子头 | v1 **关闭**：`黑旋风` 本身不像人名，作 canonical_name 会污染实体表 |
| `X人氏` | 涿郡人氏 | 要求地名后缀字（郡/县/州…），挡住「乃本地人也」 |

裸用 `A字B` 的精度很差——红楼的「知书识字」「闺阁字样」「十字街口」、水浒的「帅字旗」全会命中，
所以这条规则单独用会把误报灌进库。这就是 `NOT_NAME_CHARS` 那张黑名单存在的原因。

规则抽不到的（对话里的知识、伏笔、称谓变化）本模块**不猜**，全部留给 LLM 抽取。因此本文的
召回率只针对「注入的矛盾」，不代表抽取器召回。

## 4. 注入矛盾后的召回

注入方式是给库里已有的 canon 断言**再写一条同主语、同谓词、同槽位但取值不同**的断言，记下
其 id；然后看引擎报告的 evidence 里是否出现这个 id（不是看问题数）。

| 作品 | 注入 | 检出 | 召回 | 注入后问题数 | 注入后分数 |
| --- | --- | --- | --- | --- | --- |
| 红楼梦 | 3 | 3 | 100% | 5 | 60.0 |
| 三国演义 | 40 | 40 | 100% | 44 | 0.0 |
| 水浒传 | 40 | 40 | 100% | 72 | 0.0 |

合计 83/83。

水浒注入 40 条却报 72 条问题，这不是误报，账能对上：一个 finding 是**一条原有断言 × 一条伪造
断言**的配对，同一（主语, 谓词）组里若本来就有 *o* 条真实断言、又被注入了 *f* 条伪造值，就产生
*o × f* 条。实测 40 条伪造值落在 36 个组上（4 个组被连注两次），组内真实条数为 1/2/3/5，于是
`Σ(o×f) = 21×1 + 6×2 + 5×3 + 2×4 + 3×2 + 5×2 = 72`，与引擎报告的 72 条完全一致。

顺带暴露一个真实分布事实：水浒里同一主语的 `has_name` 最多堆到 **5 条**（同一人物在多个回目被
重复介绍，规则各抽一遍）。这正是 §5 那条 O(n²) 边界会踩到的输入形态——205 条断言时组内最多 5 条
还无感，但它会随篇幅线性长大。

红楼的 3 条是它全部可用注入点，样本太小，只能说明「注入即检出」这条路径通，不能当召回率看。

## 5. 规模曲线：只消掉同值副本那一半，取值全不同仍是 O(n²)

在**独立干净库**上做，每个尺寸都从干净备份开始，只复制该分支的真实 canon 断言。两条曲线只差
一件事：副本是挂在同一实体同一槽位，还是各自挂在独立实体上。

| 断言条数 | 同槽位副本（修复前） | 同槽位副本（分桶后） | 独立实体 |
| --- | --- | --- | --- |
| 2,111 | 0.133 s | 0.018 s | 0.021 s |
| 5,111 | 0.409 s | 0.054 s | 0.061 s |
| 10,111 | 1.696 s | 0.085 s | 0.130 s |
| 20,111 | 7.311 s | **0.186 s** | 0.257 s |

读法：

- 修复前同槽位：断言每翻倍，耗时 ×3.1 / ×4.1 / ×4.3 —— 逼近 **O(n²)**；20,111 条 7.311 s。
- 分桶后同槽位：每翻倍 ×3.0 / ×1.6 / ×2.2 —— 在**这张表所测的输入形态下**（每组 181 份取值完全相同的副本）回到近似线性；20,111 条 **0.186 s（快 39 倍）**。这张表衡量的是「同值副本把组撑大」这一个场景，不能外推成「N 条同槽位事实的复杂度变线性」。
- 独立实体：每翻倍 ×2.9 / ×2.1 / ×2.0 —— 表级本来就线性，用来做对照。
- **未解决的边界（t52 独立验收实测）**：把 n 条**取值互不相同**的断言放进同一槽位时，分桶不起作用（每桶 1 条），配对次数仍是 C(n,2)——n=10/20/40 实测 **45 / 190 / 780** 次，逐次翻倍 ×4.22 / ×4.11，是二次增长不是线性（来源：`docs/verification-dedup-2026-10-24.md` §二 配对比较次数实测，探针包装 `_classify_object_conflict()` 直接计数）。所以「7.31 s → 0.186 s」是**重复密集场景**的实测提速，不是所有输入从 O(n²) 变 O(n)。

绝对秒数随机器负载浮动（同一命令两次跑，修复前 20,111 条分别 7.31 s 与 3.24 s），所以看**翻倍
倍数**而不是绝对值：修复前同槽位每翻倍 ×3.1–5.1，修复后 ×1.6–3.0，独立实体 ×1.9–3.0。
「修复前超线性、修复后与独立实体同量级」这个定性结论多次运行一致——但同样只对**同值副本密集**的输入成立，取值全不同时恢复 C(n,2)（见上一条）。

### 根因

耗时取决于**每个（实体, 谓词, 槽位）组里有几条**，不是表里断言总数。复制时每组被塞了 181 份取值
完全相同的副本，`_same_value()` 会提前跳过、不产生问题（曲线里 findings 全 0、分数全 100），但
**比较次数照走**——逐对调用 `_canonical()` 做 `json.dumps` 才是那 7.3 秒的来源。

这不是假想的输入形态：本批 205 条真实断言里，同一主语的 `has_name` 已经堆到 5 条（同一人物在
多个回目被重复介绍，规则各抽一遍，见 §4）。百万字按比例外推，单组 50–100 条是现实的，修复前
单次 `analyze` 会落在秒级。

### 修法

组内先按 `_canonical(取值)` 分桶，只枚举**跨桶**配对：同值两条按定义不可能构成取值冲突，所以
去重不改变任何 finding 语义。但复杂度要说准——跨桶配对数是

    Σ_{i<j} m_i·m_j = (n² − Σ m_i²) / 2      （m_i 为第 i 个桶的条数）

- 全部同值（k=1 个桶）：0 次配对，这是 20,111 条那一行的情形；
- 取值全不同（k=n，每个 m_i=1）：**C(n,2)**，与修复前完全相同；
- k≥2 个取值、每桶 n/k 条：Θ(n²)，只是常数变小。

所以准确说法是「从 O(n²) 降到桶大小之积」，**最坏情形仍是 O(n²)**；只有同值副本占多数时，桶大小之积才近似等于 finding 数。
实现见 `backend/moyu_consistency.py` 的 `_detect_fact()`（`buckets` / `bucket_list` 两层循环），
设计说明见 `docs/consistency-engine.md` §1。

### 分桶键与语义等价不是同一套关系

分桶键是 `_canonical(取值)`（`json.dumps(sort_keys=True)` 的文本），判定语义等价的是 `_same_value()`
（走 `_normalize_for_compare()`，把 `1` 与 `1.0` 视为同值）。两者不完全等价：`1` 与 `1.0` 的 JSON
文本不同，会落进**不同桶**，于是这一对仍会被比较一次。

代价只是多比较一对常数开销，不会多报冲突——真正的判定在 `_classify_object_conflict()` 开头仍先调
`_same_value()`，命中即返回「不构成矛盾」。t52 探针实测：`1` 与 `1.0` 比较 1 次、0 findings（来源：
`docs/verification-dedup-2026-10-24.md` §三 与 §四 P2）。反方向没有反例：`_canonical` 的文本等价
强于 `_normalize_for_compare`，同一 canonical 文本必然同一语义取值，所以不会「同桶但语义不同」而漏报。

### 等价性怎么证的

不是靠推理，是逐条比对：

| 比对面 | 结果 |
| --- | --- |
| 21 个（库, 分支）组合（含 4 档规模曲线库、独立实体库、注入后的三部分支） | finding id 集合 / 严重度 / 标题 / 分数 / `examined` **全部一致** |
| 最坏用例：同槽位 3 个取值 × 50/40/30 条重复 | 新旧都报**恰好 4,700 条**（`50×40+50×30+40×30`），id 集合一致 |
| 同槽位 2,000 条完全相同取值 | 新旧都报 0 条 |

回归用例已固化进 `tests/consistency_fixtures.py`（p9/b9：4700 条精确计数 + 2000 条同值必须 0 条 +
每条 finding 的两侧取值必须不同）。

## 8. 已知局限

1. **抽取器不是 LLM**：本文证明的是「真实原文 → 断言 → 引擎」这条链路通，不是「AI 抽取质量」。
2. **注入是规则级伪造值**：它检验检测器的判定逻辑，不检验抽取器自身的错抽。
3. **红楼统计太薄**：3 条事实断言，召回数字不能当召回率。
4. **只注入了 fact/attribute 冲突**：时间线、知识越界、关系称谓、伏笔这四类在真实语料上没有
   可用注入点（它们需要从对话里抽，正是 LLM 抽取器要补的部分）。
5. **单机单进程**：没测并发、没测多项目同时 analyze。
