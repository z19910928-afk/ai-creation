## 0. 一句话结论

**四项交付做完了，一项没做完，一项做完了但作者还用不上。**
Q1 五项里 3 项达标、1 项范围缩水、1 项指标未达且未接生产。
最重要的发现不是「差 2.2 个百分点」，而是：**续写引擎躺在仓库里，生产链路一次都没调用它**。

### 1.1 一致性引擎的真实处境

「7 类 vs 计划 3 类」听起来是超额，但必须说清楚它意味着什么：

- **能力**上确实是超额：fact / timeline / knowledge / attribute / relation / foreshadow / evidence 七类检测器 + 分数 + 等级封顶 + 发表门禁 + 前端面板 + HTTP 契约，全部有测试。
- **证据**上是缩水的：计划要 30 万字 × 3 部真实作品，实际只有 1 部 10.5 万字的**合成**数据。
  合成数据的生成器与引擎同源，recall 100% / 误报 0 这个数字**不能外推到真实稿件**。
  它证明的是「引擎能检出按规则注入的矛盾」，不是「引擎在真人写的稿子上好用」。

结论：**能力超前，证据落后**。Q1 真正欠的不是代码，是真实语料上的一个数字。

### 1.2 预算续写的真实处境

v1.0 → v1.1 的账：

| | v1.0 | v1.1 | 变化 |
|---|---|---|---|
| 全部场景 | 14/20 = 70.0% | 16/20 = 80.0% | +10.0pt |
| 3000 字（Q1 目标） | 6/9 = 66.7% | 7/9 = **77.8%** | +11.1pt，差 2.2pt |
| 平均轮数 | 3.20 | 3.85 | +0.65 |
| 翻转 | — | fail→pass: sc-16、sc-17；pass→fail: 0 | 无回归 |

**提升全部来自「弹性轮数」一个机制**：`extended_rounds=12`，只作用在 sc-16、sc-17 两个 underpowered 场景。
v1.1 另外两个新机制——「停滞重试」`retries=1`（只触发 sc-18，**没救活**）、「停滞提示」`stall_hint_rounds=1`
（同样零产出）——**加起来贡献 0 个翻转**。

换句话说：**v1.1 加的三个机制里，两个白加**，有效的那一个是用轮数换通过率——平均轮数从 3.20 涨到 3.85。
这 0.65 轮是真实成本：同样的稿子要多花约 20% 的模型调用。这个代价必须写进成本账，不能只报通过率。

**一个必须记录的基准瑕疵**：`ENGINE_VARIANTS` 只把 `max_stall_retries` 与 `hard_max_rounds` 钉死成
v1.0 语义，**没有 pin `closing_hint`**——它是 t14 新增、默认开启的，所以「v1」变体并不是 v1.0 的逐字节复现，
而是「v1.0 的两个显式参数 + v1.1 的余量提示」。本次数值不受影响，因为基准里的 `FakeProvider` 只**观测**
提示、不消费提示（`run.py` 注释已写明「provider 本身不因提示改变产出」）。
但这意味着：**换到真实模型时，`closing_hint` 会改变产出，那时 v1/v1.1 的对照就不再干净**。
下一轮要么把 `closing_hint` 也参数化，要么在真实模型基准里承认这一项不可归因。

仍未通过 4 个（v1.1）：

| 场景 | 档位 | 目标 | 实际 | 停止原因 | 性质 |
|---|---|---|---|---|---|
| sc-15 | volatile | 4000 | 4661（+261） | target_reached | **超冲**：单轮爆字，引擎无法回收 |
| sc-18 | stalling | 3000 | 46 | no_progress | **模型不动**：重试 1 次仍 46 字 |
| sc-19 | budget_limited | 3000 | 2318（−382） | budget_exhausted | 外部预算中断（非引擎缺陷） |
| sc-20 | canceled | 4000 | 2157（−1443） | canceled | 作者主动取消（非缺陷） |

其中 sc-19、sc-20 本来就不该算引擎失败——它们是「外部打断」的真实场景，通过率为 0 是正确结果，
不该被计入「一次通过率」的分母来拉低指标。**当前 80% 的分母里混进了 2 个不该通过的场景**，
这是基准口径的可改进项（见 §4 P1-4）。

## 2. 一致性引擎的误报来源分类

从 `docs/consistency-engine-spec.md` 的「已知误报来源」逐条汇总，归为 7 个主题。
按「真实写作中会不会常态发生」排序 —— 越靠前越该优先修。

### 主题 A：时间维度缺失（最高频，人物弧光的杀手）

| 具体 | 影响类别 |
|---|---|
| 任一侧缺 `valid_start`/`valid_end`，`_overlap` 保守返回真 | fact、attribute |
| 「先记一条，后面才补时间」的真实写作流程 → 本应分属不同时期的取值被判冲突 | fact、attribute |
| `known_by` 是静态集合，无法表达「角色在第 30 章才知道」 | knowledge |
| 有意变更没有有效期区分：性格「沉稳→暴躁」是合法弧光，无有效期就报 high | attribute |

**为什么最高频**：墨屿的写作流程是「先写，再补设定」，不是「先建完整设定卡再写」。
作者补有效期之前，任何一次属性变化都会报错。这是**结构性误报**，不是规则没调好。

### 主题 B：语义归一不足（等价取值被判冲突）

| 具体 | 影响类别 |
|---|---|
| `_same_value` 不处理单位、大小写、字符串↔数字（`"20"` vs `20`）、数组顺序 | fact |
| `attribute` 检测器用**原始字符串比较**（`value_json ==`），不是 `_same_value`；`{"a":1}` vs `{"a": 1}` 报 high | attribute |
| 关系类型不做同义词/称谓归一（师父/师傅/师尊） | relation |

**注意**：`attribute` 这一条是**已知的不一致**——`fact` 已经改用 `_same_value`，`attribute` 还留着原始比较。
属于「修了 A 没修 B」的同类遗漏，成本低，应该尽快对齐。

### 主题 C：身份与作用域不归一（结构性误报）

| 具体 | 影响类别 |
|---|---|
| `known_by` 只做精确字符串匹配，**不匹配别名**（写「阿砚」匹配不上「沈砚」）→ spec 自述「最常见的结构性误报来源之一」 | knowledge |
| `known_by` 元素不 trim：`" 沈砚 "` 不匹配 `"沈砚"` | knowledge |
| 实体作用域是**作品级**，跨分支关系端点被误认为存在 | relation |
| `deleted_chapters` 查询无作品/分支条件（靠 id 全局唯一兜底） | timeline、foreshadow |
| `source_span` 与 `latest_revision` **不按分支过滤**，且用全库 `rowid` 判「最新」 | evidence |

**为什么严重**：分支是墨屿的核心能力（候选比较、分支写作）。一个跨分支就误报的检测器，
在真实使用中会直接摧毁信任——作者会学会忽略所有 high。

### 主题 D：状态字段未参与判定

| 具体 | 影响类别 |
|---|---|
| `candidate_memory.status` 查了但没用，`rejected`/`stale` 记忆仍驱动知识判定 | knowledge |
| `character_state` 没有 `status` 字段，已废弃/被替代的状态仍参与比较 | attribute |
| `relation` 的 `note` 不参与判定，无法区分「曾经的师徒」与「当前的师徒」 | relation |
| `reviewed_by`/`reviewed_at` 只判空，空白字符串 `" "` 能通过 | evidence |

### 主题 E：文学意图无法判定（可能是合法写法）

| 具体 | 影响类别 |
|---|---|
| 自指关系（「心魔」「自我对话」）报 medium | relation |
| 同一对人物在不同阶段有多条 active 关系 → low 提示 | relation |
| 同章节多个 `event_time`（倒叙、插叙、同章多场景） | timeline |
| 同序位多章节（并行叙事、群像） | timeline |
| `stage` 任意非 `payoff` 值只要有老 plant 无 payoff 就触发 15 章超期 | foreshadow |

**处理原则**：这一类**不该靠规则消灭**，该靠「降级 + 允许作者标记误报」。
当前 v1 没有 finding 台账（spec §8.2 已承认），所以作者只能改源数据，不能「这条我知道，忽略」。

### 主题 F：硬编码阈值与宽松转换

| 具体 | 影响类别 |
|---|---|
| 伏笔 15 章阈值硬编码，无卷/部边界 | foreshadow |
| `int()` 不是严格整数校验：`5.9` 静默截断为 5，`int("5")` 也通过 | timeline |
| 日期只做字符串比较，`_iso` 只认 `YYYY-MM-DD` 前缀，不校验 `2026-13-99` | timeline |
| `max_ordinal` 含空章节占位，会把「当前进度」推高导致伏笔误判超期 | foreshadow |

### 主题 G：数据质量提示混入业务矛盾

| 具体 | 影响类别 |
|---|---|
| `object_json` 非法 JSON 产生 medium「不是合法 JSON」——是数据质量提示，不是矛盾 | fact |
| 组内两两比较：n 条不同取值产生多条 finding，不能自动合并 | fact、attribute |
| 多证据条目重复报：一条断言引用多个失效 span，每个 span 一条 high | evidence |

**这条对产品的影响**：作者看到「3 条事实矛盾」时，可能其中 2 条是同一组的配对放大、
1 条是坏 JSON。计数与分数会显得比实际严重。**finding 需要「按断言聚合」的展示层**。

### 2.1 误报治理的优先级判断

| 主题 | 修的成本 | 修完的收益 | 建议 |
|---|---|---|---|
| A 时间维度 | 中（改 `_overlap` 策略 + 缺有效期降级为 medium） | **极高**（人物弧光不再误报） | **P0** |
| C 身份作用域 | 中（别名表 + 分支过滤） | **极高**（分支写作是核心卖点） | **P0** |
| B 语义归一 | 低（`attribute` 对齐 `_same_value`） | 中 | P1 |
| G 数据质量混杂 | 低（展示层聚合 + 分类改名） | 中（分数可信度） | P1 |
| D 状态字段 | 中（要加字段/迁移） | 中 | P2 |
| E 文学意图 | 高（需要 finding 台账 + 作者裁决） | 高但依赖台账 | P2 |
| F 阈值 | 低（可配置化） | 低 | P2 |

## 3. 过程复盘（做对了什么、做错了什么）

### 做对的

1. **先建基准再谈优化**。v1.0 的 70% 是冷启动数字，没有它就说不清 v1.1 的 +10pt 值不值。
2. **每轮都留确定性 digest**。`--repeat 2` + 逐字节一致，让「重跑结果不同」这类问题不可能被掩盖。
3. **门禁只拦有把握的类别**。只拦 fact/knowledge/evidence 的 blocker+high，不拦 timeline/attribute/relation/foreshadow
   ——因为后四类误报率还没压下来。宁可漏拦，不可错拦。
4. **验证员真的抓到了东西**。P1（knowledge_scope 字符串 → 500）、P2（空白差异 → high → 导出 409）都是
   会直接炸用户的白屏级 bug，靠自测没发现，靠外部静态审查+探针发现。
5. **文档不许写裸行号**。t13 把 66 处行号改成符号名，避免了「改完代码文档全错」。

### 做错的

1. **契约设计错误（最该记的一条）**：把「结果指标达标」（3000 字 ≥80%、续写已接生产）写进了
   **verification 任务的 acceptance**。verification 的职责是「核查并如实记录」，不是「让指标达标」。
   结果这个任务永远无法判定通过，只能中途 amend 契约。
   **教训**：结果指标属于 implementation 的 verify 或复盘的整改项；verification 的 acceptance 应当是
   「核查动作是否完成、证据是否充分、结论是否如实」。
2. **交付了引擎没接线**。t8/t14 花了大量篇幅把引擎打磨到 33 个用例、11 项基准验收，
   但没做「作者点续写会发生什么」这一端到端验证。**功能交付的判据是「作者能用」，不是「测试通过」。**
3. **单人写测试会漏掉整类问题**。`tests/consistency_fixtures.py` 的 `main()` 从未调用 `seed_clean`，
   「干净项目 100 分」是对着不存在的项目假通过了好几天——而且正是 P7 的 bug 让这条断言一直绿。
   **教训**：断言必须能在实现错误时失败；「100 分」这类正向断言尤其要配一个能证伪的场景。
4. **编排失误**：t4/t11 的 dependencies 传了空数组 + approval=automatic，导致验证任务在开发中途就启动，
   无法再编辑依赖。**教训**：验证任务必须显式依赖全部实现任务，宁可晚启动。
5. **覆盖了不该覆盖的产物**：v1.0 基线 `budgeted-baseline.json` 被后续 `run()` 重写（digest 从
   `6aa37fc9…` 变 `f3afbcf9…`），旧文件没备份。虽然字段值零差异，但「发布的基线」不该被静默改写。
6. **验证独立性全程降级**：6 个成员的模型路由（workbuddy 池）402 积分耗尽，所有验证最终由实现者本人执行。
   报告里已明示「不是第三方验收」，但这仍然是本阶段最大的方法学缺陷。
7. **基准变体没 pin 全**：`ENGINE_VARIANTS["v1"]` 只钉了 `max_stall_retries`/`hard_max_rounds`，
   没钉 `closing_hint`（t14 新增默认开启）。当前 `FakeProvider` 只观测不消费提示，数值未受影响；
   但换真实模型后 v1/v1.1 对照会被这一项污染。**教训**：新增默认开启的行为，必须同时进「变体参数表」，
   否则历史基线就不可复现了。

## 4. 下一阶段优先级

### P0 — 不做就等于 Q1 没完成（1–2 周）

1. **预算续写接进生产**。`process_ai_job` 对 `task=="continue"` 且有 `target_characters` 的作业
   用 `run_budgeted_continuation` 驱动多轮；逐轮正文落进同一候选；轮数预算接进 `app_quota_reservation`；
   前端显示「已写 1,850 / 3,000 字，第 2 轮」。
   **验收**：干净库 + 假 provider 的 HTTP 级回归，证明一次「续写」请求真的走了多轮、额度按轮扣、
   作者能看到进度。
2. **真实语料基线**。拿 1 部真实 10 万字以上稿件（作者自己的作品即可）跑一致性引擎，
   记录真实 findings 数、人工判定误报数、真实误报率。
   **验收**：`docs/consistency-realworld-2026-XX-XX.md`，含逐条人工判定与误报率。
   **说明**：没有这一步，「检出 100%、误报 0」只是合成数据上的自我安慰。
3. **3000 字通过率 77.8% → 80%**。两条路选一条：
   - 修 sc-15 超冲（volatile 档：单轮爆字 → 引擎需要「溢出不可回收」的显式失败，而不是算进 target_reached）；
   - 或承认 sc-19/sc-20 不该进分母，重算通过率口径（当前分母混入 2 个必然失败的场景）。
   **建议先改口径再补能力**——用错的分母优化出来的数字没有意义。

### P1 — 误报治理（2–3 周）

4. **主题 A：时间维度**。缺 `valid_start`/`valid_end` 时由 high 降为 medium，并在 finding 里明示
   「补上有效期即可消除」；`known_by` 加时间轴（或至少在文档里承认这是 v2 能力）。
5. **主题 C：身份与作用域**。`known_by` 支持实体别名（读 `entity.aliases_json`）；
   `deleted_chapters`、`source_span`、`latest_revision` 全部按分支过滤。
6. **主题 B：`attribute` 对齐 `_same_value`**（一行改动 + 一个 fixture）。
7. **主题 G：finding 按断言聚合**，展示层一个断言一条，详情里列配对；坏 JSON 从"矛盾"改名为"数据质量"。

### P2 — 产品化（Q2 起）

8. **finding 台账表**（`finding.id` + 内容指纹），支持作者标记「已确认 / 误报 / 延后」。
   这是主题 E（文学意图）的唯一正确解法，也是「一致性分数」能被信任的前提。
9. **`character_state.status`** 与 `candidate_memory.status` 参与判定。
10. **伏笔阈值可配置**（按卷/部），`int()` 改严格整数校验。
