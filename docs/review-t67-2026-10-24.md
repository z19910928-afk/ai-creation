## 五、findings 与 requiredFix

### F1（medium）非 2xx 详情「先截断后脱敏」，跨边界泄漏前缀

`backend/moyu_extract.py:519-522`：

```python
if status < 200 or status >= 300:
    raise ExtractProviderError(
        "provider_error", _redact(f"HTTP {status}：{payload[:200]}", self.api_key)
    )
```

`_redact`（`:557-564`，单串替换）只能匹配**完整** key；`payload[:200]` 先切断后，
跨边界的 key 只剩前缀，匹配不上。实测（探针 J）：

```
provider.transport = lambda ...: (403, "X"*195 + "sk-t68-httppath-abcdefgh")
detail 尾部 = "...XXXXXXXXXXXXXXXXXXXsk-t6"      # 泄漏 5 字符前缀
provider.transport = lambda ...: (403, "X"*100 + key)  # 对照：全键在 200 内
detail 含 "***"、不含完整 key                      # 说明脱敏本身是好的，问题只在顺序
```

可达性：需要网关在 4xx 响应体里回显请求头/凭据（部分网关在错误 JSON 里带
`request.headers`），且回显位置跨过第 200 字符。**这不是 t67 引入的**——t62 起该行就是这个顺序，
t64/t67 只修了 curl stderr 那条路径；但它属于同一类缺陷，且违反 t62 报告里「API Key 不能出现在
detail 里」的承诺，故按当前字节记为 medium。

**requiredFix**：先脱敏再切片，例如

```python
safe_body = _redact(payload, self.api_key)[:200]
... f"HTTP {status}：{safe_body}"
```

并补一条 fixture：`transport` 返回 `(403, "X"*195 + key)`，断言 `key not in detail` 且 `key[:5] not in detail`。

### F2（low）`content[:200]` 完全不脱敏

`backend/moyu_extract.py:536`：`invalid_json` 详情直接拼 `content[:200]`，没有任何 `_redact`。
实测（探针 J）：content 里回显完整 key → detail 完整泄漏。可达性低（调用方不会把 key 放进 prompt，
只有模型/网关异常输出才可能回显），但修复成本一行。

**requiredFix**：`_redact(content[:200], self.api_key)`（或先 `_redact(content, ...)[:200]`）。

### F3（low）回归用例声称的「跨 200 边界」并未发生

`tests/extract_fixtures.py:907`：`("A" * 180 + short_key, …)` 长度 187 < 200，
`[:200]` 不会截断任何字符，因此这条用例锁的是「短 key 也要登记」而非「跨边界」。
同一句注释（`:906`）与 t67 自述都写成「跨 200 边界」。我的探针用 196+7=203 复验过**行为正确**，
所以这是证据精度问题，不是行为缺陷。

**requiredFix**：把该场景改为 `"A" * 196 + short_key`（203 字符，真正跨界），
或补第四组用例；注释同步改成与实际长度一致。
