# 墨屿超越 NovelForge 的战略方案

- 日期：2026-10-23
- 方法：Amazon Working Backwards（PR/FAQ → 竞争不对称 → 路线图 → 验收）
- 前置输入：`docs/novelforge-gap-analysis-2026-10-23.md`（12 维差距矩阵）

---

## 0. 核心判断：不要在他們的记分牌上比赛

NovelForge 的记分牌是：**卡片类型数、工作流节点数、提示词模板数、stars 数**。在这张牌上你已经落后 1.4–5.9 倍代码量、1255 个 star、13.5 个月迭代，全面对标需要 50–73 人周，而且永远追不完。

换一张记分牌：**作者能不能写完一本 100 万字还不崩。**

这不是话术。这是架构决定的：

| | NovelForge | 墨屿 |
|---|---|---|
| 底层假设 | 小说 = 可拆解的卡片流水线 | 小说 = 有状态的可信系统 |
| 内容历史 | 卡片覆盖即丢，无 revision | append-only + 74 个触发器 |
| 事实来源 | 无 source span | codepoint/UTF-8 双偏移 + quote_hash |
| 时间有效性 | 无 | valid_start/valid_end + story_time |
| 谁知道什么 | `known_by` 只是展示字段 | epistemic_mode 五态 + POV 知情门控 |
| 上下文上限 | 5,000 字事实配额 + SQL LIKE | BM25 + 五层召回 + 字节级预算 |
| 测试 | 1 个文件 / 9 个用例 | 111 个文件 / 1,348 个用例 |

**结论：NovelForge 的架构撑不到 100 万字。它要补这一课，必须先重写数据层——这是 6–12 个月的窗口。**

## 1. PR/FAQ（先写新闻稿，再写代码）

### 新闻稿

> **墨屿 1.0 发布：第一个能写完 100 万字的 AI 写作系统**
>
> 2027 年 X 月 —— 今天，墨屿发布 1.0。它解决了一个所有 AI 写作工具都在回避的问题：当一本书写到 50 万字，AI 会忘记设定、写错时间线、让角色说出他不该知道的事。
>
> 墨屿的一致性引擎在每次写作前检查 6 类矛盾，在交稿前给出可量化的一致性分数；每一条 AI 结论都能回到原句，每一次修改都可回滚，每一处矛盾都能在发表前被检出。
>
> 上线 12 个月，已有 N 位作者用它完成 50 万字以上长篇，平均一致性分数 97.3%，单章人工干预从 5.2 次降到 1.8 次。

### FAQ

**Q：和 NovelForge 有什么不同？**
A：他们优化"生成更多结构化内容"，我们优化"写了 100 万字还不崩"。他们是卡片工厂，我们是状态操作系统。

**Q：为什么作者要在意一致性分数？**
A：因为连载小说的读者会记得。一个 30 万字处才暴露的设定矛盾，会让前 100 章全部失效。这是唯一值得付费的质量指标。

**Q：为什么本地优先？**
A：作者的正文是资产，不是数据。不上传、不要账号、ZIP 可带走、MIT 可商用。

**Q：能写多大？**
A：100 万字实测通过，关键事实召回 ≥95%，单章上下文成本可控（见 LongFormBench）。

**Q：多少钱？**
A：本地版永久免费（MIT）。团队版（共享设定库/审稿流）另行定价。

| 层级 | 指标 | 12 个月目标 | 为什么是它 |
|---|---|---|---|
| **北极星** | 50 万字以上作品完本率 | ≥30% | 唯一能证明"写长篇"的指标 |

## 3. 四支柱：三攻一守

### 支柱 1（旗舰）：一致性引擎 Consistency Engine

**六类矛盾检测**

| 类型 | 例子 | 检测依据 |
|---|---|---|
| 事实矛盾 | "万法阁在青云城" vs "万法阁在西域" | assertion 冲突 + 同实体多值 |
| 时间矛盾 | 第 3 章说三年后，第 40 章说五年前 | story_time + 事件序 |
| 知识越界 | 配角说出只有主角知道的秘密 | epistemic_mode + known_by + POV |
| 属性漂移 | 性格/能力/外貌无理由突变 | character_state 快照 diff |
| 关系/称谓矛盾 | 上一章"师父"这一章"师兄" | 关系图 + 称谓表 |
| 伏笔断线 | 埋下未回收 / 回收无铺垫 | plot_thread 生命周期 |

**检测管线（复用现有数据，不新建体系）**

```
结构化候选（SQL on assertion/character_state/plot_thread）
  → 候选对生成（同实体、同时间窗、同关系）
  → LLM 判定（带两侧 source_span 原文）
  → 规则校验（排除合理反转/作者计划）
  → 作者裁决（确认/误报/延后）
  → 回写 assertion（带 evidence）
```

**输出物**
- **一致性分数**：`max(0, 100 - Σ 每条问题的严重度权重)`，绝对扣分，按卷/章展示。权重 blocker=20 / high=8 / medium=3 / low=1；分数只由问题本身决定，不随筛选器变化（`--min-severity` 只裁剪清单，不改分数）。等级 A≥90 / B≥75 / C≥60 / 其余 D，并且存在 blocker 时最高 C、存在 high 时最高 B——分数分段不能盖过最严重的问题。
- **发表前门禁**：分数低于阈值时阻断导出，作者可覆盖但需理由（复用现有终稿门）
- **矛盾台账**：可筛选、可分配、可标记误报

**验收（Q1 末）**：3 部 30 万字测试书 + 注入 100 个矛盾 → 检出率 ≥75%、误报 ≤15%、定位到句 ≥85%。
**验收（Q2 末）**：6 类全开 → 检出 ≥85%、误报 ≤10%、定位 ≥90%。

### 支柱 2：可验证 AI Verifiable AI

| 能力 | 现状 | 目标 |
|---|---|---|
| 每条 AI 结论带来源 | 部分（章后分析） | 100%：无来源必须显式标注"推断" |
| 逐条裁决 | 整段 modal 对照 | 行内 diff，逐条接受/拒绝（CodeMirror 6） |
| AI 决策日志 | 有 request_audit | 可导出、可按章回看、可对比模型 |
| 模型能力矩阵 | 9 用途路由 + 单次探测 | 7 项能力探测 + 自动降级建议 |
| 无来源事实进 canon | 可能 | 0 条（硬门禁） |

**卖点一句话**："AI 说的每一句话，你都能点回去看原文。"

### 支柱 3：百万字长程 Long-horizon

| 能力 | 现状 | 目标 |
|---|---|---|
| 分层压缩 | 书→卷→章→场景已有 | 每级滚动摘要 + 关键事实索引 |
| 检索 | BM25 + 五层召回 | 加结构化查询（"上次提到 X 是哪章"） |
| 预算 | 字节级确定性裁剪 | 加成本可视化（每千字 token/费用） |
| 召回验证 | 无 | 100 万字测试集，前 10 章事实召回 ≥95% |
| 上下文模板 | 无（全自动） | 作者可编程模板（借 A 的 @DSL，但叠加 POV/时间过滤） |

### 支柱 4（防守）：受控自动化 Controlled Automation

**不做 26 节点 DAG。** 做 8 个动作 + 3 个触发器，每步都有作者门：

| 动作 | 说明 |
|---|---|
| 读章纲 | 取本章任务卡 + 上级摘要 |
| 生成候选 | 续写/润色/扩写，带预算 |
| 一致性预检 | 跑支柱 1 的检测 |
| 字数校验 | 复用 output_contract |
| 作者裁决 | 必须人工确认（不可跳过） |
| 写回正文 | revision + diff |
| 更新记忆 | candidate → 待确认 |
| 生成摘要 | 章后滚动摘要 |

| 触发器 | 说明 |
|---|---|
| 章纲保存 | 自动准备候选，不自动写入 |
| 章完成 | 自动跑分析 + 一致性预检 |
| 日更计划 | 按目标字数排期，提醒而非代写 |

**卖点一句话**："自动化，但每一步你都能否决。"——与 NovelForge 的"全自动流水线"形成对照。

## 4. 基准即武器：LongFormBench

**为什么这是最高杠杆的动作**：NovelForge 全仓只有 1 个测试文件、无 CI，它**无法产出任何可信的质量数字**。你先定义基准，你就是标准制定者。

### 基准设计

| 项 | 设计 |
|---|---|
| 数据集 | 10 部 50 万字公开小说（版权合规）+ 5 部合成长文 |
| 注入 | 每部注入 20 个已知矛盾（6 类各若干），共 200 个 |
| 指标 | 检出率、误报率、定位到句准确率、关键事实召回率、每千字成本、单章干预次数 |
| 复现 | 开源脚本 + 固定模型版本 + 固定 prompt 版本 |
| 发布 | 每季度一份《中文长篇小说 AI 写作一致性报告》 |

### 对比呈现（示意）

| 指标 | NovelForge | 墨屿 |
|---|---|---|
| 矛盾检出率 | 无此能力 | 90% |
| 误报率 | — | 8% |
| 100 万字事实召回 | 无测试 | 95% |
| 单章人工干预 | 未知 | 1.8 次 |
| 自动化测试 | 9 个用例 | 1,348 个用例 |

**这张表比 1,256 个 star 更有说服力，因为它可复现。**

## 5. 12 个月路线图

### Q1（1–3 月）：地基 + 基准

| 交付 | 验收 |
|---|---|
| 许可证统一（MIT，修 package.json） | LICENSE/package.json/README 三处一致 |
| 一致性引擎 v1（事实/时间/知识越界 3 类） | 30 万字 × 3 部，检出 ≥75%、误报 ≤15% |
| LongFormBench v0.1 开源 | 脚本可复现，报告公开 |
| 提示词工坊（模板 CRUD + 内置保护 + 重置） | 内置 22 个模板可查看/克隆，克隆成自定义后才可编辑；内置可用重置恢复出厂正文（10 个 AI 任务全覆盖） |
| 多轮字数预算续写 | 3000 字章，一次通过率 ≥80% |

> **Q1 实测（2026-10-23）**：3000 字章一次通过率 **77.8%（7/9）**，**未达成 ≥80%**。差距原因是生成侧对长度提示零响应——基准用的是对抗式 provider（不读 `max_characters`、`stall_retry_min_characters` 及任何其他提示），sc-15 在第 1 轮就写出 4661 字、越过 4400 上界 261 字，sc-18 每轮只写 12–30 字、轮数上限 24 也到不了 2700 下限；同一引擎在「模型服从提示」假设下的上界见该报告附录 A，但那不是计入 headline 的数字。所以这条验收本身缺少「模型服从度」假设，属指标口径缺陷（详见[预算续写引擎 v1.2 复测](consistency-budget-v1.2-2026-10-23.md) §6、§7）；作为参照，全部 20 场景的一次通过率为 80.0%（16/20，v1.0 为 70.0%）。

> **一致性引擎 v1 的实测口径（2026-10-23）**：单部 40 章 / 105,182 汉字合成库，注入 35 条矛盾，召回 100%（35/35）、干净库 0 误报、单次分析中位 6.72 ms。**Q1 原定的「30 万字 × 3 部真实作品」验收尚未执行**——当前数字来自合成数据，且生成器与检测引擎同源，属于自测而非独立验证（局限见[一致性引擎 v1 · LongFormBench 基线](consistency-baseline-2026-10-23.md)）。

## 7. 明确不做

| 不做 | 理由 |
|---|---|
| 通用工作流编排器（26 节点 DAG） | 20–28 人周，对手已领先，且其引擎无 if/else、无循环、scheduler 是死代码 |
| 前端全量 Vue/TS 重写 | 10–12 人周，用户零感知 |
| 云同步 / 多人实时协作 | 破坏"本地优先、数据主权"的核心定位 |
| AI 全自动写小说 | 与"作者控制"定位直接冲突 |
| 追 stars 数字 | 结果不是目标；先做完本率 |
| Linux 全量支持 | 1.5–2 人周可做，但 ROI 低于一致性引擎 |

## 8. 风险与对冲

| 风险 | 概率 | 影响 | 对冲 |
|---|---|---|---|
| 一致性引擎误报高，作者烦 | 中 | 高 | 先做"高精度低召回"，误报可一键标记并进规则库；分数可关闭 |
| 百万字测试成本高 | 高 | 中 | 合成数据 + 抽样 + 缓存；基准只在发版前跑全量 |
| 单人开发带宽不足 | 高 | 高 | 严格按复制时间表排序；Q4 生态可延后 |
| NovelForge 转向一致性 | 低 | 高 | 它要先重写数据层，窗口 6–12 个月；用基准报告抢占话语权 |
| 作者不愿看"分数" | 中 | 中 | 分数默认折叠，只在发表前提示；提供"一键修复建议" |

## 9. 如果只能做三件事
