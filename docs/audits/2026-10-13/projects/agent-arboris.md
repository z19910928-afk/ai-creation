## 结论

Arboris 的可借鉴重点是“创意对话 -> 可编辑蓝图 -> 章纲 -> 多候选 -> 人工选择 -> 下一章参考已写摘要”的作者流程。多作品书架、个人模型设置、按对话/环境/心理/节奏选择润色维度也有实际页面入口和后台调用链。

它不能作为“高级功能已经全面成熟”的证明。当前普通页面没有调用高级写作入口、定稿记忆入口、六维审查入口；护栏修复函数断裂，章节选择后的检索入库缺参数，角色可见性仍会泄露秘密，普通向量检索没有章节时点过滤。可见伏笔页面实际使用关键词分析，而不是持久化伏笔的编辑、回收接口。

墨屿已有候选确认、证据记忆、追加正文历史、材料预览、基础导出等基础能力，不能全算缺失。核心差距是把创作产物真正写回章纲/场景/回顾，把事实与人物知情范围统一用于生成，并解决采纳、保存、恢复的可靠性。不能用星数、表数量、服务类数量或模拟通过来宣布文学质量达到第一梯队。

## 上游完整调用链与实际断点

### 可达基础创作链：E

1. 书架创建/读取作品：`NovelAPI.createNovel/getAllNovels` -> `/api/novels` -> `NovelService.create_project/list_projects_for_user`。每作品单独 uuid 与 user ownership，保存到数据库。
2. 概念对话：`sendConversation` -> `/concept/converse`；从数据库读已存 history，模型返回结构化对话控制，保存 user/assistant 消息。
3. 生成蓝图：`generateBlueprint` -> `/blueprint/generate`；从概念历史提炼有效内容，验证 Blueprint，再写蓝图、角色、关系、章纲；作者编辑通过 save 或 patch 保存。
4. 生成/续生成章纲：`generateChapterOutline` -> `/chapters/outline`，带当前蓝图与已有章纲，写回 `ChapterOutline`。没有证明长篇章纲质量；大纲结果直接更新落盘，不是独立待采纳候选。
5. 普通生成：`generateChapter` -> `/chapters/generate`，读选定旧章、生成缺失摘要、章导演脚本、过滤蓝图、可选检索，逐个生成差异风格正文和可选版本评审，写 `ChapterVersion`，等待人工确认。
6. 版本选择：`selectChapterVersion` -> `/chapters/select` -> 选定版本和 successful；随后入库因缺 `user_id` 发生异常，捕获后仍返回成功。作者已保存正文与“检索材料更新完成”不是同一状态。
7. 下一章读旧章 `selected_version` 与 `real_summary`，属于可达消费路径。入库失败时旧章摘要仍可能被正文生成，但它不是可靠的全书检索闭环。

### 高级能力不能算普通作者已可用

- `backend/app/api/routers/__init__.py:8,14-17` 注册 writer、增强 analytics、伏笔、项目和审查路由，不能据此算完整 UI。
- `/advanced/generate` 确实调用 `PipelineOrchestrator`，可带预设/配置组合。`pipeline_orchestrator.py:150-217` 准备创作规则、人格、伏笔/派系、记忆与两阶段检索；`267-317` 准备审查/修稿。普通前端 `frontend/src/api/novel.ts:224-249` 使用旧接口，不使用 advanced。
- `/chapters/{chapter_number}/finalize` 确实选正文并调 `FinalizeService`，服务有全局摘要、角色状态、剧情线、快照逻辑；页面选版本调用 `/novels/{project_id}/chapters/select`，没有走 finalize。`finalize_service.py:369-386` 将全角色状态存成 `__all__` 原始文本，不是各人物的逐事实、可追溯、可审查状态。
- 两阶段检索使用 LLM 生成查询、模型过滤为剧情/角色/世界/技法。`knowledge_retrieval_service.py:203,382-385,394-395` 依赖另一种 `ChapterBlueprint`。普通章纲只写 `ChapterOutline`，未找到普通前端把这些增强章节蓝图完整准备好的链。即使高级接口运行，还需要补输入数据/异步数据库桥接验收。
- reader simulator、自我反思不因服务文件存在就算有效能力。`pipeline_orchestrator.py:40-57` 默认关闭；`349-395` 既没在预设中打开 reader/self-critique，也未把它们加入可覆盖字段；ultimate 还明确关闭。
- 人物知识管理测试是独立模块演示；普通写作使用 `WriterContextBuilder`，不是该演示 manager 的完整知识约束。
- 不需要把孤立高级功能数当作墨屿必补数量。优先补作者能稳定完成的流程。

## 可以借鉴与不应照搬

可以借鉴的产品设计：

- 创意讨论变成编辑得动的蓝图，讨论结果不是一段复制文本。
- 章纲有标题、摘要并能继续扩展，正文生成直接消费已保存章纲。
- 同一章给多个明显不同方向的候选，让作者比较选择，最终选择需影响后续上下文。
- 对话、环境、心理、节奏四种润色维度比笼统“润色”更贴近作者意图。
- 书架和按作品隔离；作者能在页面配置模型，无需改命令行。
- 下一章消费前章摘要和结尾；写后处理应有明确进度和错误，不只标 successful。

不应照搬：

- 用字符串出现过就推断人物已知全部秘密。
- 只提示模型“不要泄露”而没有在检索前做时点/知情范围硬过滤。
- 失败审稿给80或100分。
- 选版成功与索引更新成功合用一个成功标记。
- 重生成删除旧版本、手改原地覆盖历史。
- 使用后台文件数量或“ultimate”预设名推断作者获得了完整高级能力。
- 模型输出摘要/状态直接覆盖正典，不保留逐事实的来源/确认。
- 从上游复制代码、提示词或素材。本固定快照 README 有 MIT 徽章，但未找到 LICENSE 文件且官方元数据许可为空，不能视为已解决许可来源；本报告只借鉴设计。

## 墨屿可执行改进工作

P0：影响保存正确性和信任，先修。P1：形成完整创作流程。P2：进一步改善效率、出版或效果。任务不以具体框架/数据库品牌定义。

| A2 / P0 | 修复证据漂移、拒绝状态加载、删除后备份恢复；先于新记忆自动化。 | 修改前文和恢复备份不会把作品卡死。 | 已确认引句前加文字，保存成功并把来源标待复核；拒绝记忆后重开作品正常；删除一章后恢复旧完整备份，能恢复原编号和正文，事务无半成品。 |

## 第一梯队的验收定义

“第一梯队”是同条件对照后的作者收益，不是排行榜口号。应分三层验收：

1. 可信基础：所有 P0 实际问题修好；自动保存、候选采纳、证据失效、备份还原、失败重试没有静默丢稿；连续20次核心流程和故障插入得到确定结果，保存失败不得显示已保存。
2. 可用创作链：独立作者从一句话创意完成蓝图、章纲、候选比较、写后确认、下章检索、伏笔回收、终稿导出，不需进入后台或复制数据；桌面/手机实页复验。
3. 长篇效果：使用相同故事设定、模型、上下文预算和总花费，至少覆盖短篇收束与较长跨章故事，对七项目有能力的对应任务做盲测。检索用真实索引 Recall/Precision，时点/知情泄露硬门为0；文学质量、续写可采纳率、作者修订时间和反复改写一致性另行测量，先登记门槛，不能事后调指标。

评测必须保留作品状态、实际查询、召回证据、发送材料、模型响应、采纳和审稿处理记录，才能归因于产品而不是换了更贵模型。

本轮没有收费真实模型对照，也没有 Arboris 整机部署/真实页面测试，因此**文学质量、长篇效果及生产稳定性仍为 U**。本报告支持改造优先级和验收设计，不支持宣称墨屿已经完成改造或已经超过七项目。

## 交叉复核建议

请另一名代理复核以下六点，不能把本报告仅做汇总：

1. frontend 是否存在 advanced/finalize/六维接口调用；如果有，指出真正路由和渲染父组件，修改“后台”的判定。
2. 护栏配置存在时返回 None 及重写段缩进位置，复跑组件探针。
3. 普通 select 缺 user_id 与数据库已选定后吞错的顺序。
4. 角色秘密/未来章材料未硬过滤；区分“潜在召回”与真实向量检索概率。
5. 伏笔页面使用 analytics 关键词模型，是否存在另一个被路由实际加载的持久化伏笔编辑入口。
6. 墨屿 outline/scene/summary/check 的采纳是否只是复制，基础审查是否只为规则检查；不要把已有历史、备份、关系时间线错写成缺失。
