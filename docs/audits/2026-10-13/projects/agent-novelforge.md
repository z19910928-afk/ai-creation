# NovelForge 专项审查：作者流程、卡片上下文与确认边界

审查日期：2026-10-13。角色：NovelForge 项目专责；仅阅读固定快照、执行离线组件探针并形成报告，没有修改产品、推送、发布或收费模型请求。

## 结论

NovelForge 最值得墨屿学习的是作品模板、卷/阶段/章节卡片树、结构化设定、按任务选择材料、选区改稿预览，以及“提取变化→作者修改确认→保存设定→下一次生成消费”的操作链。墨屿已具备章节任务卡、候选确认、原文证据、服务器修订、材料选择和故事结构基础，不能说完全没有这些能力；主要差距是基础能力尚未连接成顺畅的长篇创作流程。

NovelForge 也不能作为可靠性和小说质量的已验证标杆。它的卡片历史只在浏览器保存20条；伏笔建议是启发式占位，未找到作者页面消费；状态记忆没有来源修订/原句/有效时点约束，部分类别满额后丢掉新确认项；运行状态可持久化，但调度控制仍在进程内。墨屿应独立实现它的产品思路，同时保留并修好自己的证据、修订和人工裁决边界。

## 三条完整源码链

### 1. 项目模板到章节正文

作者选模板 `components/ProjectCreateDialog.vue:106-115` → 作品写入 `services/project_service.py:52-68` → `project.created`触发雪花初始卡 → 核心蓝图和分卷/阶段工作流生成父子卡 → 阶段章纲按连续章号校验 → `bootstrap/workflows/阶段大纲.wf:29-54`创建章纲与正文卡 → `bootstrap/card_types.py:232-245`正文按实体/阶段/章号选材料 → `CodeMirrorEditor.vue:2585-2604`进入生成请求。

这是E源码可达链，没有真实模型验收。项目创建已commit后模板事件失败会被忽略，`project_service.py:70-72`，不能把“作品已创建”当作“模板全部成功”。阶段列表校验失败得到空列表`阶段大纲.wf:24`，后续仍清空来源`64-69`，同样不应作为无失败的批处理模板。

### 2. 普通正文到动态记忆再到下一次写作

作者点击人物动态提取 → `CodeMirrorEditor.vue:3452-3468`发送当前正文与参与者、显示可编辑预览 → `3475-3507`确认`updateDynamicInfoOnly` → `api/endpoints/memory.py:176-185`通用`apply_preview(character_dynamic)` → `memory_extractors/character_dynamic.py:44-59` → `memory_service.py:643-659,668-731`按项目/标题找到人物卡并commit → `CodeMirrorEditor.vue:3517`重新读取卡片 → 模板`card_types.py:237`取dynamic_info → `CodeMirrorEditor.vue:1283-1303`解析卡片 → 后续生成context_info使用。

人物的预览弹窗在CodeMirrorEditor内，人物走`updateDynamicInfoOnly`；场景/组织/物品/概念走通用`applyMemoryPreview`。不能把它们错误归为一个不存在的独立预览组件。关系提取另有预览、入图和关系材料消费。

这条链E成立，但有四个应主动避开的缺口：

1. 动态项只有id/info，`schemas/entity.py:32-35`，请求没有来源修订/摘录hash，不能在原文改动后判断该预览是否仍有效。
2. 根据标题找人物卡，`memory_service.py:643,668-670`，不是稳定实体ID；改名、同名与异类同标题需要另行防护。
3. 心理快照保留最新，其他类别保留前N条，`memory_service.py:709-716`；类别已满时新确认项可能被追加后裁掉。重复确认只append，`694-707`，缺少幂等键和内容合并。
4. 删除先独立commit，新增后commit，`659,729`；人物状态成功后再单独更新本章参与者，`CodeMirrorEditor.vue:3508-3517`。发生中途失败可形成部分写入；应给明确部分成功状态或建立事务。

墨屿已有source_span、修订、原句验证`server.py:2272-2323`，这部分应保留并修复，不能被“更自动的提取”替换掉。

## R探针与旧文档纠偏

1. **旧调度器不是耐久优先级队列。** `workflow/engine/scheduler.py:19-22`为进程内`asyncio.Queue`；`46,82`按FIFO放入/取出，priority只是元组字段。R组件探针：先运行1，再排入priority100的2和priority-100的3，结果顺序`[1,2,3]`；取消排队的3返回false且仍执行。只证明这个原类，日志为模拟，未运行数据库或工作流。
2. **不能把旧类缺陷泛化到当前工作流。** 当前`api/endpoints/workflows.py:521-556`、`run_manager.py:114-119,154-196`和`triggers.py:210-212,328`都用`WorkflowRuntime`。`runtime.py:31-40,66-100`用共享并发槽、进程内集合控制；`state_manager.py:27-79`确实保存运行/节点状态。E支持作者暂停/恢复入口，完整服务重启、中途收费请求和重复副作用未测U。应将旧文档`docs/comparison-six-projects-2026-10-12.md:87`的“scheduler持久化运行队列、优先级”改为准确分层说明。
