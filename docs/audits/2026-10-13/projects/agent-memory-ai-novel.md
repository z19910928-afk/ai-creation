## 2. 最重要的判断

墨屿落后的核心是“写作任务和记忆维护尚未闭环”，不只是页面数量少。Ai-Novel 已将写作输入、近期摘要、生成摘要、向量检索、运行记录、批量任务等串接；墨屿目前仍大量依赖人工填表、显式标签和复制 AI 输出。墨屿已有的原句证据、人工确认、版本审计值得保留，这是可以形成差异的基础。

Ai-Novel 也不是完美标杆。当前版本退役了旧结构化记忆、Worldbook 和项目表格（README:268-288），代码的 memory pack 与 vector query 没有当前章节、POV、outline 过滤参数。不能依据旧文档或表名判定它具备全部高级记忆能力，也不能照搬这种边界。

## 4. 墨屿本轮运行复现

运行方式：导入当前 `server.py`，使用 `unittest.mock.patch` 仅替换 `state_from_db` 和 `story_map` 输入，直接执行现有 `ai_context` 和 `bounded_context_memory`。没有外部模型、网络、生产数据库，也没有修改源码。

输入是三个章节，当前为第2章，POV 为林岚。第1章的第1200字符处有“月牙密钥藏在左靴内侧”，第3章保存“林岚的父亲是最终凶手”。附带一个来源第3章、有效 span 的 accepted memory，一个第3章 timeline，以及仅 `entities=['villain']` 可知道的状态。

实际输出：

```json
{
  "evidence_found_in_old_chapter": true,
  "selected_old_chapter": true,
  "evidence_present_in_selected_excerpt": false,
  "future_memory_ids": ["m_future"],
  "future_timeline_ids": ["t_future"],
  "villain_only_states_exposed_to_hero_pov": ["secret_villain_only"],
  "memory_cap_zero_returns": 1
}
```

这些结果证明相应组件有材料截断和范围边界问题，不能据此声称已经量测真实模型的矛盾率。`memory_top_k=0` 仍返回一条是另一个小缺陷：server.py:287-295 的 break 发生在 append 后。

## 5. 关键瓶颈排序

1. **P0：先修保存、恢复和证据编辑的可靠性。** 数据可靠性由根代理/可靠性专责实测；没有这个前提，更多智能功能会放大损失。本文的重点不是替代这些复测。
2. **P1：资料是否真的送对。** 当前召回章中段缺失；取前N设定/记忆而非相关材料；本次作者要求不参与召回。入口、索引、片段选择必须统一。
3. **P1：所有材料遵守故事时点和 POV。** 现有过滤只处理人物状态的显式范围；人物允许知情列表未检查，未来记忆与 timeline 进入当前章节。旧字段没有范围会直接放行（server.py:464-467），不能当默认安全。
4. **P1：写后不再靠标签和剪贴板。** 普通小说文字不会有显式标记；摘要、状态、伏笔须成为可预览的候选变化，与章节提交及索引任务联动。
5. **P1：审稿的名称和实际检查能力要一致。** 现在“审查本章 passed”是基础完整性检查。不能用该状态证明人物、因果、时间、伏笔无矛盾，也不能把任意评分当文学质量分。
6. **P1：整章润色输入范围与覆盖范围一致。** 当前章节上下文最终只留末尾12000字符（server.py:583、347-349），app.js:73 却可替换整章。超过范围时应转为选区润色或分段任务，显示哪些内容会被修改，禁止尾段结果覆盖未提供的前文。
7. **P2：预算估计与实际模型匹配。** 墨屿把 JSON 字符数/4 命名 upper_bound（server.py:306、589），不能据此保证中文模型输入 token 上限；Ai-Novel 已至少区分中文字符（prompt_budget.py:6-21），它也仍是启发式。优先用适配器可用的 tokenizer 或保守估计，预留系统提示/输出余量，记录供应商实际 usage。
8. **P2：测评要跑实际系统。** 当前 knowledge fixture 的输入是手工 predictions，不经过 ai_context；本轮已证明实际上下文可暴露测试标签未涵盖的知识边界。测试绿色只证明 runner 的计算逻辑。

## 7. Ai-Novel 值得借鉴与不宜照搬

值得借鉴：作者要求参与检索；层次化历史；多纲/细纲章节映射；检索材料有数量、耗时、裁剪与禁用原因；批量任务暂停/恢复；生成摘要直接进对应字段；模块边界清晰。

不宜照搬：

- 不把所有计划和未来章节检索结果无区别送给当前正文生成。Ai-Novel 的 smart context 有过去章过滤，额外 memory/vector 链路却只按 project。
- 不用无版本/hash/确认约束的记忆替代墨屿既有证据链。
- 不从旧 README 推导当前存在 Worldbook/结构化图谱/分形记忆。当前版本明确退役旧表；memory_modules 中还有 tables 默认字段，但 retrieve pack 的允许 sections 仅 story_memory/semantic_history/vector_rag（memory_service.py:13-19，memory_retrieval_service.py:23-27）。
- 不把用户可操作默认流程等同于接口所有能力：前端默认 `semantic_history=false`、`memory_query_text=null`（useChapterGeneration.ts:159-171）；后端能接手工 query 不代表现有页面给作者入口。
- 不把依赖 PG、Redis、Chroma 或“多代理”本身当质量优势。墨屿可先继续 SQLite/FTS，加可替换检索与可恢复任务，等规模实测需要后再升级。
- 不把上游 CI 绿灯当没有缺陷。当前 known_issue 步骤 continue-on-error，前端全量 lint 也非硬门禁（ci.yml:119-124、217-221）；这体现工程债公开，并不自动否定其已有工作流。

## 8. 交叉复核问题

请其他代理独立核对：墨屿当前最新 HEAD 是否改变上述行号/链路；整体素材裁剪是否还产生来源范围漂移；同名角色与别名是否真正有编辑/合并/拆分的可撤销入口；角色状态来源 assertion 被撤回后是否仍注入；整章润色是否有当前正文比12000字符长时的阻断；题材/风格/Prompt 模板是否只是预览而未应用；批量候选是否实际保留作者确认边界。
