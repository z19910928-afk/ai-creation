## 核心结论

固定基线是单作品原型，已有本机数据库保存、追加正文版本、候选确认、原句证据、材料预览、关系与时间线、最小 EPUB 导出。基线实际页面中，连续输入、AI 采纳、记忆拒绝和长章润色都出现了影响作者信任的问题。本轮已进入产品修复，增加多作品工作台、可靠保存、候选范围保护、章后记忆、任务中心、备份和导入导出；基线失败与修复后的证据分别记录，不能将基线缺陷直接当作当前结果。

最需要追平的是：**可靠保存和候选保护；多作品与卷章场景规划；普通正文的章后记忆；按故事时点和人物知情范围检索；可定位、可处理的审稿；可停止、可恢复、受预算约束的任务。** 更换框架、增加模型数量或堆更多菜单不能直接解决这些问题。

当前交付包括基线审查、修复实现和本机回归。工程验证使用临时数据库、离线组件或本机免费模拟模型，作者原稿未被用作实验材料；本轮只验收电脑端，手机记录保留为历史补充。最新[第十二轮真实文学诊断](literary-pilot-v12/report.md)首对942/868字均超600至850字门，输出合格0/6、有效评审0/12，未扩后两题或发送盲评。含独立协议诊断累计31条请求预留、49642个可信完整tokens与已知下界，10条缺完整用量、实际金额未知；具体原件和范围见[评测说明](../../evaluations/README.md)。七个应用的同条件文学盲评未完成，仍未证明第一梯队。GitHub基线旧版自动检查已有成功记录，本轮增强版等待推送后的实际运行结果，不能提前记远程通过或公网部署验收通过。

## 改造顺序

1. **先保稿。** 修保存、采纳、证据漂移、拒绝回读、恢复、长章覆盖和旧审稿放行。补真实浏览器失败路径。
2. **统一身份与任务。** 让每个作品、章节、原稿版本、候选、任务都有明确归属；接通现有局部修改和任务控制；费用状态与重试身份一致。
3. **接通创作主线。** 书架→创意蓝图→卷/章/场景→材料→候选→作者确认→章后摘要与事实→下一章。
4. **做好长篇。** 段落检索、别名、时点与知情过滤、递进摘要、伏笔证据和跨章审稿，所有派生材料随改稿过期。
5. **证明效果，再扩展。** 完整备份和导入往返、真实作者流程、同模型同预算文学盲评；高级排版、插件、多端协作按实测需求增加。

建议继续使用现有本地服务和 SQLite（本机数据库），沿功能拆清保存、任务、检索与创作流程，不先做全盘重写。每个工作包的依赖、修改范围、作者收益和通过标准见[第一梯队路线](roadmap.md)。

## 第一梯队如何验收

“第一梯队”在这里是待验证的目标。应同时通过四项：

- **保稿：** 错章、重复采纳、静默覆盖、保存失败假成功及恢复失败均有可执行反例和防回归验证。
- **完整流程：** 作者在电脑端从一句话创意写到章后确认、下一章备料、伏笔收束及终稿导出，无须进后台或手动搬运结构化结果。当前不将手机端列为发布门槛，已有手机记录保留为历史补充。
- **长篇资料可信：** 实际检索和实际发送材料经过标注评测；未来、知情、跨书、跨分支、陈旧证据泄漏在规定样本中为 0，同时报告必要材料召回。
- **效果和成本：** 相同素材、模型、参数及预算下，比对文学盲评、矛盾、候选采纳率、作者改稿时间和实际用量。继续在用户已授权范围内执行收费模型评测，未知用量或价格不能记零。

不能由测试数、表数、星数、演示截图或模型分数直接授予该结论。
