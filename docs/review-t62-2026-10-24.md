## 五、F1 复现与 requiredFix

**复现**（探针 T8d，真实进程边界）：

```sh
# 假 curl：stderr 先写 180 个 'A'，再写真实 key，然后 exit 7
printf '%s%s' "$(printf 'A%.0s' $(seq 1 180))" "$KEY" >&2; exit 7
```

`OpenAIProvider(...).__call__` 抛出的 `ExtractProviderError.detail` 末尾实测为：

```
...AAAAAAAAAAAAAAAAAAAAsk-t63-SECRET-abcdef
```

即 key 的前 19 个字符被保留。根因在 `backend/moyu_extract.py:681`：

```python
detail = _redact_secrets(
    f"curl {reason}（退出码 {code}，请求超时设定 {seconds:g} 秒）：{stderr.strip()[:200]}",
    headers.values(),
)
```

`stderr.strip()[:200]` **先截断**，`_redact_secrets` **后脱敏**；截断点落在凭据中间时，
完整凭据串已不复存在，替换匹配不到它，前缀因此泄漏（provider 层的 `_redact(detail, api_key)`
同样只能匹配完整 key，救不了）。

**requiredFix**：先脱敏再截断，例如

```python
stderr_tail = _redact_secrets(stderr.strip(), headers.values())[:200]
detail = f"curl {reason}（退出码 {code}，请求超时设定 {seconds:g} 秒）：{stderr_tail}"
```

并加一条 fixture：runner 返回 `(7, "", "A"*180 + key)`，断言 `key[:10] not in error.detail`。

## 六、真实模型覆盖边界（明示，不得写成「已通过」）

1. **真实外部服务未由本报告验收**：本机 shell 缺 `MOYU_EXTRACT_BASE_URL` /
   `MOYU_EXTRACT_MODEL` / `MOYU_EXTRACT_API_KEY`，`--mode openai` 真实调用 exit 2。
   「urllib 403 / curl 200」的**网关指纹差异**是 captain 侧的真实服务观察，我复核的是
   **代码是否把根因处理落在默认路径**（§三 T1/T2/T3），不是复验网关行为。
2. **captain 的 CLI 冒烟只证明闭环**：`benchmarks/real_corpus/extract.py --mode openai
   --book 红楼梦 --limit 1 --repeat 1`（dummy key + 本地假服务）产物
   `/tmp/moyu-transport-smoke.json`：`mode=openai`、1 章 6774 字、`assertions=0`、
   `rejected=0`、`determinism={'repeat':1,'identical':True}`、`wall_s=0.013`、
   `engine.sha256` 与 §零 同值。它证明 **CLI → 默认 curl → 响应解析** 闭环，
   **不证明**外部真实模型的召回率、限流、计费与超时行为。
3. **Windows 未实测**：`--config -`（配置走 stdin）、请求体走临时文件、`json.dumps` 转义
   路径，在 curl 的 Windows 构建上语义相同，但我没有 Windows 环境，属于静态推断而非实跑。
4. **超时语义**：进程级硬杀 = 请求超时 + 15 秒余量（`CURL_TIMEOUT_MARGIN`），因此 curl
   挂死时调用方最多多等 15 秒；这是有意的余量设计，不是缺陷，但写进了残余风险。
5. **3xx 不跟随**：未传 `-L`，302/307 会以 `provider_error` 暴露而不是静默跟随；对当前
   直连 `/chat/completions` 的用法无影响。
